# Building and reproducing

Everything in [`README.md`](../README.md) can be reproduced from this tree.
The host builds need only a C99 compiler; the Cortex-M4 results need the
board.

## Host

```sh
make test-all     # both verification harnesses
make bench-csv    # timings, written to bench.csv
make memory       # peak RSS, and on Linux a massif profile and leak check
```

The verification harnesses exit 0 when every check passes and 1 otherwise, so
they can be run from CI without parsing their output.

## Cortex-M4

### Toolchain

On macOS:

```sh
brew install --cask gcc-arm-embedded    # arm-none-eabi-gcc
brew install stlink                     # st-info, st-flash
```

The core compilation flags are

```
-mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16
```

All three FFT sources cross-compile with no warnings under
`-Wall -Wextra -Wshadow -Wundef`.

### Build and flash

```sh
cd target && make       # -> build/target.elf, .hex, .bin
st-flash --connect-under-reset --reset write build/target.bin 0x8000000
```

`--connect-under-reset` is required. Without it the write fails with
`Failed to read core_id` even though `st-info --probe` reads the chip
perfectly well. A running STM32CubeIDE can also hold the probe; close it if
connection problems persist.

`st-info --probe` should report `chipid: 0x431`, `dev-type:
STM32F411xC_xE`, 512 KB flash and 128 KB SRAM. No mass-storage volume appears
for this board, which is why flashing goes over SWD rather than by copying a
file.

### Reading the output

The firmware reports over USART2, which reaches the host through the
ST-Link's virtual COM port at 115200 8N1 — `/dev/cu.usbmodem*` on macOS,
`/dev/ttyACM*` on Linux. It repeats on a loop, so the port can be attached at
any time without having to catch the boot.

No terminal emulator is needed, but on macOS one detail matters: the port's
line discipline is reset when the last file descriptor closes. Running
`stty -f /dev/cu.usbmodem... 115200 raw` and then `cat` on the same device
reads garbage, because the settings are discarded when `stty` exits and
before `cat` opens it. Set the line discipline on the descriptor you then
read from — `termios.tcsetattr` in a short Python script is enough.

## The `target/` project

Generated by standalone STM32CubeMX from `target/target.ioc`, with
Toolchain/IDE set to **Makefile**. STM32CubeIDE locks that dropdown to itself
and cannot emit a Makefile project. The HAL drivers are vendored under
`target/Drivers`, so the tree builds without CubeMX installed.

Clock configuration: HSE bypass at 8 MHz from the ST-Link's MCO, PLL
M=4 N=72 P=6 for a 24 MHz SYSCLK, AHB prescaler 1, and `FLASH_LATENCY_0`.
Only SYS (Serial Wire) and USART2 are enabled. The reasoning behind 24 MHz is
in the README's platform note.

The study's own code lives in `target/App/`, outside the directories CubeMX
regenerates:

| file | role |
|---|---|
| `cycles.[ch]` | DWT `CYCCNT` timing, plus `cyc_lock`/`cyc_unlock` to mask interrupts across a measured region |
| `console.c` | `__io_putchar` retarget so `printf` reaches USART2 |
| `app.[ch]` | `app_main()`, called from `main()`'s USER CODE 2 marker |
| `kat.[ch]` | generated by `tools/gen_kat.c`; not edited by hand |
| `ref_{emu,native}_{fft,fpr}.c` | wrappers instantiating the unmodified reference under distinct `FALCON_PREFIX` values |
| `refdrv_body.h` | shared driver implementation, included once per backend |
| `ref_{emu,native}_drv.c` | backend selection and `REF_FN` naming |
| `myfft_drv.c` | build 3 driver |
| `verify.[ch]` | runs every build against every known-answer case |
| `bench.[ch]`, `benchdrv_body.h`, `benchbuf.[ch]` | the per-operation timing sweep and its shared buffers |

### All three builds in one image

`inner.h` documents `FALCON_PREFIX` as existing precisely so that several
versions of the reference can coexist in one application, and there are no
non-`Zf()` globals to collide. Each backend needs its own translation unit,
because `fpr` is a different type under each — a raw `uint64_t` under
`FALCON_FPEMU`, a struct wrapping a `double` under `FALCON_FPNATIVE` — so one
unit cannot call both. The backend is selected by `#define` inside the
wrapper `.c` files rather than by a compiler flag, because the CubeMX
Makefile compiles every source with identical flags.

Running all three from one image at one clock setting is what makes the
comparison fair: no variation in build configuration can leak into the
measured difference.

## Regenerating the known-answer vectors

`__int128` does not exist on 32-bit ARM, so the exact schoolbook oracle
cannot cross-compile. It runs on the host instead, and its results are frozen
into a generated source file:

```sh
clang -O2 -o gen_kat tools/gen_kat.c
./gen_kat target/App/kat.c target/App/kat.h
```

The oracle is unchanged in strength; only where it runs has moved.

## After regenerating from CubeMX

CubeMX rewrites the Makefile and the linker script wholesale, so two edits
have to be re-applied by hand. Opening the `.ioc` preserves anything inside
the `/* USER CODE BEGIN */` … `/* USER CODE END */` markers, but nothing
outside them.

1. **`target/Makefile`** carries a block marked `study additions -- RE-APPLY
   AFTER ANY CubeMX REGENERATION`. That block, and the `OPT` setting, must be
   restored. `OPT` is `-O3` here rather than the generated `-Og`, to match
   the host benchmarks.

2. **`target/STM32F411xx_FLASH.ld`** has `_Min_Heap_Size` raised from the
   generated `0x200` to `0x8000`. `myfft.c` builds its twiddle tables on the
   heap, and they need 24 560 bytes across `logn` 1–10; `0x4000` is not
   enough and fails at `logn = 10`.

## Known limitation

The link uses `-specs=nano.specs`, and newlib-nano's `printf` drops
floating-point conversions unless `-u _printf_float` is added to `LDFLAGS`.
This is irrelevant to integer cycle counts, and is why the firmware reports
precision as a whole number of bits rather than as an error magnitude. It
would need adding before any harness could print a floating-point value.
